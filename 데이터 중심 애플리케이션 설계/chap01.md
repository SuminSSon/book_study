# 1장: 신뢰할 수 있고 확장 가능하며 유지보수하기 쉬운 애플리케이션

Part 1. 데이터 시스템의 기초

### 데이터 시스템 추상화
1. 데이터베이스
2. 캐시
3. 검색 색인(search index)
4. 스트림 처리(stream processing)
5. 일괄 처리(batch processing)

### 소프트웨어 엔지니어링의 목표
- 신뢰성(Reliability): SW결함, human error, 재난같은 상황에서도 시스템은 올바르게 동작
- 확장성(Scalability) : 트래픽이 증가해도 대응 가능
- 유지보수성(Maintainability) : 모든 사용자가 시스템 상에서 생산적으로 작업할 수 있어야 함


### 신뢰성
결함(fault)을 예측하고 대처할 수 있는 시스템을 내결함성(fault-tolerant) 또는 탄력성(resilient)을 지닌다 함

결함 != 장애
- 결함: 사양에서 벗어난 시스템의 구성 요소
- 장애: 사용자에게 필요한 서비스를 제공하지 못하고 시스템 전체가 멈춘 경우

-> 결함으로 인해 장애가 발생하지 않게 내결함성 구조를 설계하자!

넷플릭스의 카오스 몽키(Chaos Monkey): 고의적으로 결함을 유도하고 내결함성 시스템을 지속적으로 훈련하고 테스트함

#### 하드웨어 결함
시스템 장애율 방지 - 각 하드웨어 구성 요소에 중복(redundancy) 추가
    - 디스크 RAID 구성
    - 서버: 이중 전원 디바이스, hot-swap CPU
    - IDC: 예비용 전원 발전기

#### 소프트웨어 오류

시스템 내 체계적 오류(systematic error)는 노드 간 상관관계 대문에 하드웨어 결함보다 시스템 오류를 더 많이 발생함.

명확한 해결책이 없다. 시스템의 가정과 상호작용에 대해 주의 깊게 생각하기, 빈틈없는 테스트, 프로세스 격리, 죽은 프로세스의 재시작 허용, 프로덕션 환경에서 시스템 동작의 측정, 모니터링, 분석하기 등 알림 체계로 예방해야 함.

#### 인적 오류

사람의 오류가 75~90%임.

대응 방법
- 오류의 가능성을 최소화하는 방향으로 시스템 설계
- 장애가 발생할 수 있는 부분 분리 (sandbox 제공)
- 테스트 강화
- 오류를 빠르고 쉽게 복구할 수 있는 도구
- 모니터링 대책 마련 (지표 분석)

### 확장성

부하 증가로 인한 서버 부하를 방지하자.

부하 매개변수(load parameter)
- 웹 서버의 초당 요청 수
- 데이터베이스의 읽기 대 쓰기 비율
- 대화방의 동시 활성 사용자
- 캐시 적중률
- etc

트위터 타임라인 아키텍처
- 버전 1. 트윗을 쓰면 테이블에 전역적으로 insert. 각 유저는 타임라인 접근 시점에 join
- 버전 2: 각 유저별 트윗 오편함에 insert. 각 유저는 타임라인 접근 시, 자신의 트윗 우편함만 읽음
- 버전 3: 인플루언서는 버전 2에서 제외하고 버전 1을 사용 (hybrid)
